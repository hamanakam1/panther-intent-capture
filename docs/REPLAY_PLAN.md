# Replay plans

A capture is a record of what someone did. A replay plan turns that record
into a **proposal for re-running the same path**: where the flow went, and
what was pressed.

Panther never runs a plan. It is an export, it requires review, and it never
carries a value the capture did not record.

## What a plan contains

- **Steps.** A bounded list of `navigate`, `click`, `submit` and `change`
  steps, in the order they were recorded, each with the handle that was used
  to find the control.
- **Observations.** The page-reported failures the capture recorded, with
  their time and their status.
- **Friction.** The possible-friction hypotheses derived from the timeline.
- **Limits.** An explicit statement of what a plan can and cannot carry.
- **Authority.** `export_only`, `requires_review`, `execution_authorized:
  false` — the same fences every other Panther artifact carries.

## Choosing a handle

A replay only works if the control can be found again. Panther offers the
most stable handle it has, in this order:

| Strategy | Source | Example |
|---|---|---|
| `test-id` | `data-ticket` or `data-tab` | `[data-ticket="M-4242"]` |
| `id` | a plain, short element id | `#save-button` |
| `role-name` | an ARIA role and an accessible name | `get_by_role("button", name="Save")` |
| `text` | the visible text of a button or link | `get_by_text("Save")` |
| `href` | the target of a link | `a[href="https://example.test/settings"]` |
| `none` | nothing stable was captured | — |

A step with no stable handle is marked `replayable: false` and is left out of
the rendered script. Panther does not guess.

## What a plan cannot do

**Panther does not capture typed values.** It never reads input values,
keystrokes, or page text, and that has not changed. A `change` step therefore
records *that* a field changed, not what it became, and it is not replayable.
A plan describes the path; it cannot reproduce the data.

Screenshots are not analyzed and are not part of a plan.

## Using a plan

- `GET /api/extension/recordings/<id>/replay` returns the plan as JSON.
- `GET /api/extension/recordings/<id>/replay?format=playwright` returns a
  Playwright script.
- The review page has **Export replay plan** and **Export replay script**.

The rendered script is a proposal:

```python
# Generated by Panther Intent Capture from capture capture-123.
# This is a proposal for a person to review. Panther never runs it.
# No typed value is present, because Panther never captured one.

from playwright.sync_api import sync_playwright


def replay():
    with sync_playwright() as playwright:
        browser = playwright.chromium.launch()
        page = browser.new_page()
        page.goto("http://127.0.0.1:8080/work-board")
        page.locator("[data-ticket=\"M-4242\"]").click()
        page.locator("#save-button").click()
        browser.close()


if __name__ == "__main__":
    replay()
```

## Why this is worth having

Combined with the observations, a plan is a **reproduction specification**: the
path that was taken, and the failure that followed it. A verifier can replay
the path and check whether the failure still happens. That is the useful
combination — a plan without the observations is just a click list, and an
observation without a plan is a story.

## The contract

The plan has its own schema, `replay-plan` version 1.0, separate from the
intent bundle. It is destination-neutral: it is not an issue, not a test
file, and not a script that anything runs on its own.
